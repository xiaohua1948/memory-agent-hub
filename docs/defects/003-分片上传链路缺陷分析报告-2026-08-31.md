# 分片上传链路缺陷分析报告

- **项目**：memory-agent-hub / memory-frontend + memory-backend
- **分析日期**：2026-08-31
- **代码版本**：master 分支（上传功能首次合入后的工作区）
- **技术栈**：Vue 3.5 + Element Plus 2.9 + axios / Spring Boot + MyBatis-Plus + Redis + MinIO
- **分析范围**：前端 `src/utils/upload/uploader.ts`、`src/utils/upload/request.ts`、`src/utils/upload/hash.worker.ts`、`src/api/file/upload.ts`、`src/components/file/FileUpload.vue`；后端 `UploadController`、`UploadService`、`UploadServiceImpl`、`MinioMultipartUtil`、`UploadConfig`、`UploadTask`、`UploadCleanupTask` 及 `RedisUtil`

| 级别 | 含义 |

## 一、严重级缺陷

### 1.1 单例 Service 实例字段导致并发串数据（最严重）

**位置**：`memory-backend/.../service/impl/UploadServiceImpl.java:125-126, 502-503, 554-555, 393-395`

```java
// 125-126 行：单例 Bean 的实例字段
private ImageMetaData pendingImageMeta;
private VideoMetaData pendingVideoMeta;

// complete() 内
if ("image".equals(task.getCategory())) {
    fillImageMeta(task, fileEntity, lastModifiedTime);   // 写入 this.pendingImageMeta
} else {
    fillVideoMeta(task, fileEntity, lastModifiedTime);   // 写入 this.pendingVideoMeta
}
persistFile(userId, task, fileEntity);                   // 落库 file 主表
if ("image".equals(task.getCategory())) {
    imageMetadataMapper.insert(pendingImageMeta);        // 读取 this.pendingImageMeta
} else {
    videoMetaDataMapper.insert(pendingVideoMeta);        // 读取 this.pendingVideoMeta
}
```

**问题**：`UploadServiceImpl` 是 Spring 单例，`pendingImageMeta` / `pendingVideoMeta` 是**实例字段**，而 `complete()` 并发执行（前端 `FILE_CONCURRENCY=2`，两个文件同时走 complete）。两个图片同时上传时：

1. 线程 A `fillImageMeta(A)` → `this.pendingImageMeta = metaA`（`fileId=fileIdA`）
2. 线程 B `fillImageMeta(B)` → `this.pendingImageMeta = metaB`（`fileId=fileIdB`）
3. 线程 A `persistFile(A)` 后 `insert(this.pendingImageMeta)` → 插入的是 **metaB**

**后果二选一**：若 `image_meta_data.file_id` 有唯一约束，则其中一个线程抛异常 → 触发 catch 删对象 → 该次上传失败；若无约束，则插入两条指向同一 `fileId` 的脏数据，另一个文件的元数据永久缺失。两个视频并发上传同理（`pendingVideoMeta`）。

**触发频率**：双图/双视频同时上传是日常操作，必现概率高。

**修复建议**：去掉实例字段，改为方法局部变量。例如让 `fillImageMeta` 返回 `ImageMetaData`，`complete()` 用局部变量承接后再 `insert`；`persistFile` 之前不依赖任何共享状态。

### 1.2 chunk / complete / abort 缺少任务归属校验（IDOR）

**位置**：`memory-backend/.../service/impl/UploadServiceImpl.java:300-302, 338, 423`（配合 `UploadController.java:47-68`）

```java
// uploadChunk：只查任务存在，不校验归属
UploadTask task = requireTask(uploadId);   // 300-301 行

// complete：同样只 requireTask
UploadTask task = requireTask(request.getUploadId());   // 338 行

// abort：只 loadTask，不校验 userId
UploadTask task = loadTask(uploadId);   // 423 行
```

**问题**：`uploadChunk` / `complete` / `abort` 三个接口都拿到了 `userId`（`StpUtil.getLoginId()`），却从未执行 `task.getUserId().equals(userId)` 校验。任何登录用户只要拿到别人的 `uploadId`，就能：

- 往他人任务里塞分片（`/chunk`）
- 取消他人上传（`/abort`，还会清理对方已传分片）
- 触发他人任务的合并（`/complete`，若凑齐分片）

这属于典型的越权（IDOR）。而 2.3 的「共享任务」设计本身就会跨用户复用 `uploadId`，进一步放大了该风险。

**修复建议**：`requireTask` 增加 `userId` 参数并校验归属；`abort` 同样校验。共享任务场景需显式区分「任务创建者」与「被授权的共享上传者」。

---

### 1.3 complete 先 requireTask 后秒传兜底，共享任务并发完成时第二方误报失败

**位置**：`memory-backend/.../service/impl/UploadServiceImpl.java:338, 344`

```java
UploadTask task = requireTask(request.getUploadId());   // 338 行：任务已被清理则直接抛 41009

// 344 行：合并前再查一次秒传，本意是处理"另一线程已合并完成"
String instantFileId = instantUpload(userId, task.getFileMd5(), task.getAlbumId());
```

**问题**：两个用户共享同一任务、都收齐分片后同时调用 `complete()`。先完成的一方执行 `clearTask(task)` 删除 Redis 中的任务，后到的一方在 338 行 `requireTask` 就抛出 `UPLOAD_TASK_NOT_FOUND`（41009），根本走不到 344 行的秒传兜底。前端将这次**实际已上传成功**的文件标为「上传失败（任务不存在或已过期）」。

**修复建议**：秒传兜底应放在 `requireTask` **之前**，即先以 `request.getMd5()` 判定文件是否已入库，命中则直接返回 `instant=true`，未命中再走 `requireTask`。

## 二、中等级缺陷

### 2.1 每传一个分片就全量 listParts，整体 O(n²) 次 MinIO 请求

**位置**：`memory-backend/.../utils/file/MinioMultipartUtil.java:100-116`、`memory-backend/.../service/impl/UploadServiceImpl.java:324`

```java
// MinioMultipartUtil.listParts：逐个 statObject 探测 1..totalChunks
for (int i = 1; i <= expectedTotalChunks; i++) {
    StatObjectResponse stat = minioClient.statObject(...);   // 每片一次网络往返
    ...
}

// UploadServiceImpl.uploadChunk：每个 chunk 上传后都调一次
List<Part> parts = minioMultipartUtil.listParts(...);   // 324 行
```

**问题**：`uploadChunk` 每上传一个分片就调用一次 `listParts`，而 `listParts` 内部 `for i in 1..totalChunks` 逐个 `statObject`。对 2GB 文件（5MB/片 ≈ 410 片），累计约 `410 × 410 ≈ 16 万` 次 `statObject` 网络往返，大文件上传极慢并会压垮 MinIO。

**修复建议**：`uploadedCount` / `allChunksDone` 改用 Redis 计数器（`INCR`/`HSET`）维护，`listParts` 仅在 `pre-check`（断点续传）与 `complete` 时全量调用一次。

---

### 2.2 前端暂停在「算哈希 / 预检」阶段不生效

**位置**：`memory-frontend/src/utils/upload/uploader.ts:355-407, 281-284`

```ts
async function processItem(item: UploadItem): Promise<void> {
  if (!item.md5) {
    item.status = 'hashing';
    item.md5 = await computeMd5(item);   // 期间被 pause() 置为 'paused' 也不中断
  }
  if (item.status === 'canceled') return;   // 只判 canceled，不判 paused
  // ... preCheck 照常执行
  item.status = 'uploading';                // 400 行：无条件覆盖 paused 状态
  await uploadAllChunks(item);              // 只有分片循环里的 while(paused) 才真正响应暂停
}
```

**问题**：`pause()` 只把 `status` 置为 `'paused'`，但 `processItem` 在 `computeMd5` 之后、`preCheck` 之后都无条件继续执行，且在 400 行直接把状态改回 `'uploading'`。只有分片上传循环里 `while(statusOf(item)==='paused')`（281-284 行）真正响应暂停。结果：文件在算哈希或预检阶段点击「全部暂停」无效，会一路传完。

**修复建议**：在 `preCheck` 前与 `status='uploading'` 赋值前补上 `paused` 判断与挂起等待；或统一抽一个 `await waitIfPaused(item)` 在关键节点调用。

### 2.3 共享任务不更新 albumId、不注册用户任务

**位置**：`memory-backend/.../service/impl/UploadServiceImpl.java:208-214`

```java
// 2. 同一 MD5 已有进行中的任务 → 共享
Object cachedUploadId = redisUtil.get(MD5_KEY_PREFIX + md5);
if (cachedUploadId != null) {
    UploadTask shared = loadTask(String.valueOf(cachedUploadId));
    if (shared != null && md5.equals(shared.getFileMd5()) && shared.getFileSize() == size) {
        return shared;   // 直接返回，未写 albumId、未 registerUserTask
    }
}
```

**问题**：命中共享任务时直接返回，没有把当前请求的 `albumId` 写进任务，也没有 `registerUserTask(userId, uploadId)`。后果：第二个用户最终上传完成的文件**不会进入他的目标相册**；同时该 uploadId 未计入该用户的 `USER_TASK_KEY` 集合，`checkConcurrentLimit` 的并发上限统计失真。

**修复建议**：共享分支也执行 `existing.setAlbumId(albumId); saveTask(existing); registerUserTask(userId, uploadId)`，与续传分支保持一致。

---

### 2.4 listParts 吞掉所有异常，掩盖存储故障

**位置**：`memory-backend/.../utils/file/MinioMultipartUtil.java:110-113`

```java
try {
    StatObjectResponse stat = minioClient.statObject(...);
    result.add(new Part(i, stat.etag()));
} catch (Exception e) {
    // 该分片尚未上传，跳过
}
```

**问题**：`catch (Exception)` 把 `statObject` 的**任何**异常都当作「该分片未上传」跳过，包括 MinIO 宕机、网络超时、鉴权失败、bucket 不存在等。故障发生时，`listParts` 返回空/部分列表，`complete()` 会误报「分片未上传完整」而非「存储服务异常」，掩盖真实故障，且断点续传会误判已传分片全丢、触发重传。

**修复建议**：仅对「对象不存在」的特定异常（如 `ErrorResponseException` 且 code 为 `NoSuchKey`/`NotFound`）跳过，其余异常向上抛出并映射为 `STORAGE_ERROR`。

## 三、轻微级缺陷

### 3.1 缩略图 contentType 恒为 image/jpeg

**位置**：`memory-backend/.../service/impl/UploadServiceImpl.java:488-489, 530-531`

```java
minioOSSUtil.uploadToOSS(task.getThumbnailObjectName(),
        new ByteArrayInputStream(thumbnail), thumbnail.length, "image/jpeg");
```

**问题**：图片小于 `thumbnailThreshold` 时 `thumbnail = bytes`（复用原图字节），若原图是 PNG/GIF/BMP，缩略图对象却仍被标注为 `image/jpeg`，MinIO 元数据与实际内容不一致（浏览器通常靠嗅探能正常显示，但下载/直链场景 content-type 会错误）。

**修复建议**：低于阈值复用时按 `task.getContentType()` 传真实 MIME；仅当经 `compressImage` 重编码为 jpg 时才传 `image/jpeg`。

### 3.2 UploadTask 缺 serialVersionUID

**位置**：`memory-backend/.../model/entity/UploadTask.java:14`

```java
public class UploadTask implements Serializable {   // 未声明 serialVersionUID
```

**问题**：`UploadTask` 通过 Jackson 序列化到 Redis 再反序列化，`Serializable` 未声明 `serialVersionUID`，类结构变更时存在反序列化兼容性告警。

**修复建议**：补充 `private static final long serialVersionUID = 1L;`。

## 修复优先级建议

1. **立即修复（严重）**：
   - 1.1 实例字段并发（会直接造成脏数据/上传失败，双图并发必现，改动小收益大）
   - 1.2 归属校验（安全 IDOR）
   - 1.3 秒传兜底前置（共享任务并发完成误报）
2. **尽快修复（中等）**：
   - 2.1 listParts 性能（大文件上传体验硬伤）
   - 2.2 暂停语义（用户可感知的「全部暂停」失效）
   - 2.3 共享任务 albumId/注册（相册归属丢失）
   - 2.4 listParts 异常区分（可观测性）
3. **质量优化（轻微）**：3.1（缩略图 MIME）、3.2（serialVersionUID）

> 注：本报告基于静态代码审查，覆盖前端上传状态机与后端三阶段接口（pre-check / chunk / complete / abort）及 MinIO/Redis 交互；并发与时序类问题（1.1、1.3、2.2）建议结合实际并发上传场景做进一步验证。
